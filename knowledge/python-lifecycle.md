- invariant: Without reuselanguageinvoker, each plugin, script and context menu run gets a new sub-interpreter (Py_NewInterpreter) with empty sys.modules, so module state never survives a run; all share one process GIL, so concurrent runs serialize. A service keeps its interpreter until stopped. | check: invoker changes keep per-run isolation and service lifetime, and are judged with several plugin widgets starting at once, not one run | at: `xbmc/interfaces/python/PythonInvoker.cpp:CPythonInvoker::execute`
- trap: CScriptInvocationManager keeps one last invoker, reused only for the same script in ScriptDone state and replaced whenever any other script starts. After the main script returns, the invoker waits with no timeout for every other thread of the interpreter, so a leftover Timer delays the end of the call and blocks reuse. | check: no code or reasoning assumes reuse keeps Python state between calls, and invoker changes keep the sub-thread wait | at: `xbmc/interfaces/generic/ScriptInvocationManager.cpp:CScriptInvocationManager::GetLanguageInvoker`, `xbmc/interfaces/python/PythonInvoker.cpp:CPythonInvoker::execute`
- invariant: CPythonInvoker::stop signals Monitor abort, waits PYTHON_SCRIPT_TIMEOUT (5 s) on the calling thread, then sets SystemExit as the async exception of every thread state; it fires only at the next bytecode, so a thread blocked in a C call holds shutdown. StopRunningScripts stops scripts one after another, each wait in turn. | check: stop changes do not treat 5 s as a hard cap, teardown code tolerates SystemExit at any bytecode, and the waits of dozens of live invocations do not add up | at: `xbmc/interfaces/python/PythonInvoker.cpp:CPythonInvoker::stop`, `xbmc/interfaces/generic/ScriptInvocationManager.cpp:CScriptInvocationManager::StopRunningScripts`
- invariant: onExecutionDone runs a GC, clears every module dict and collects again before Py_EndInterpreter, so binding destructors and add-on finalizers (open sqlite connections) run in a live interpreter; the language hook is unregistered only after Py_EndInterpreter. Out of order, teardown crashes or hits SQLITE_MISUSE after a profile switch. | check: teardown changes keep destructors inside a live interpreter with the hook still registered | at: `xbmc/interfaces/python/PythonInvoker.cpp:CPythonInvoker::onExecutionDone`
- convention: Monitor, Player and window callbacks are queued and run only by the Python thread that created the object, while it sits in Monitor.waitForAbort, xbmc.sleep or Window.doModal; abortRequested() does not pump, and a plugin call that never waits never sees a callback. | check: dispatch changes keep handlers off Kodi's Announce and main threads and keep the pump in those waits | at: `xbmc/interfaces/legacy/CallbackHandler.cpp:RetardedAsyncCallbackHandler::makePendingCalls`, `xbmc/interfaces/python/CallbackHandler.cpp:PythonCallbackHandler::isStateOk`
- invariant: waitForAbort and xbmc.sleep wait in 100 ms slices, releasing the GIL and running pending callbacks between slices. Only waitForAbort returns early on abort, and it treats a timeout of 0 or less (default -1) as infinite; abortRequested() is the non-blocking check. | check: changes keep the slice pump, the GIL release and the zero-means-forever contract service add-ons rely on | at: `xbmc/interfaces/legacy/Monitor.cpp:Monitor::waitForAbort`, `xbmc/interfaces/legacy/ModuleXbmc.cpp:sleep`
- convention: Each xbmc.Monitor, subclassed or bare, registers with XBPython on construction, and every announcement is dispatched into Python once per live monitor across all add-ons. | check: announcement dispatch changes, cost per announcement with dozens of live monitors | at: `xbmc/interfaces/legacy/Monitor.cpp:Monitor::Monitor`, `xbmc/interfaces/python/XBPython.cpp:XBPython::OnNotification`
- convention: Blocking API calls (executeJSONRPC, sleep, waitForAbort, xbmcgui.Dialog methods) run under a DelayedCallGuard, which releases the GIL so the add-on's other threads keep running. | check: a new or changed blocking binding takes a DelayedCallGuard or GuiLock | at: `xbmc/interfaces/python/LanguageHook.cpp:PythonLanguageHook::DelayedCallOpen`
- external: GuiLock (getCondVisibility, ListItem and InfoTag accessors when not offscreen, Control and WindowXML calls) drops the GIL and waits for the FrameMove door; while callers wait, each frame sleeps 1 ms per 4 calls served since the counter reset, at least 2 ms, at most 10 ms during unpaused video and 80 ms otherwise. The counter resets after 5 frames with no waiter, so steady polling grows the sleep, and back-to-back calls in one open door hide it from a microbenchmark. | check: a PR adding GuiLock to a binding or polling through one, judged by frame time under steady calls | at: `xbmc/interfaces/legacy/AddonUtils.cpp:GuiLock::GuiLock`, `xbmc/application/Application.cpp:CApplication::FrameMove`
