- convention: Win32 file and directory calls go through CWIN32Util::ConvertPathToWin32Form, which adds \\?\ (or \\?\UNC\ for smb:// and \\server paths) so paths past MAX_PATH work. Windows does not normalize prefixed paths, so the helper fixes forward and duplicate slashes and ".." itself; invalid UTF-8 returns an empty string. | check: new Windows file code passes paths through ConvertPathToWin32Form or the CFile layer, not a W API on a raw converted string, and handles the empty result | at: `xbmc/platform/win32/WIN32Util.cpp:CWIN32Util::ConvertPathToWin32Form`
- trap: CWin32File never opens with FILE_SHARE_DELETE, so deleting or renaming a file Kodi still holds open fails where POSIX unlink succeeds. | check: delete, rename or replace logic closes every CFile handle on that path first | at: `xbmc/platform/win32/filesystem/Win32File.cpp:CWin32File::Open`
- trap: Kodi directory paths end with a separator, but the FindFirstFile based Win32 stat fails on a directory with a trailing backslash; CWin32File::Stat strips it. A failure there breaks directory fasthashes, so folders rescan every time. | check: Windows code that queries a directory through a Win32 call strips the trailing separator | at: `xbmc/platform/win32/filesystem/Win32File.cpp:CWin32File::Stat`
- trap: FromW and ToW with an explicit length convert exactly that many units, so a length that counts the terminator puts an embedded NUL in the result. | check: buffers passed to the Win32 converters use a length without the terminator | at: `xbmc/platform/win32/CharsetConverter.cpp:KODI::PLATFORM::WINDOWS::FromW`
- scenario: One optical drive arrives as "D:\" from GetLogicalDriveStringsW, "D:" from storage events, \\.\D: for device access, in either letter case. CMediaManager::TranslateDevicePath strips the slash and uppercases the letter; raw keys fail to match removal to insertion and ejected discs stay listed. | check: drive or disc code that stores or compares drive paths normalizes them through TranslateDevicePath first | at: `xbmc/storage/MediaManager.cpp:CMediaManager::TranslateDevicePath`
- external: The raw ::FileTimeToLocalFileTime and ::LocalFileTimeToFileTime apply today's UTC offset, not the one in force on that date, so times shift an hour across DST. KODI::TIME::FileTimeToLocalFileTime goes through SystemTimeToTzSpecificLocalTime; LocalFileTimeToFileTime and GetTimezoneBias wrap the raw calls. | check: conversions of past or future dates use the TzSpecific path, not the raw calls | at: `xbmc/platform/win32/XTimeUtils.cpp:KODI::TIME::FileTimeToLocalFileTime`
- trap: A lock file, even with FILE_FLAG_DELETE_ON_CLOSE, survives a crash or OS freeze and blocks the next start. Kodi detects a running instance with a named mutex, which the OS frees when the process dies. | check: single instance or lock logic uses a kernel object that dies with the process, not a file on disk | at: `xbmc/platform/win32/WinMain.cpp:CheckAndSetGlobalMutex`
- convention: DEVMODE dmDisplayFrequency is an integer, so 23.976, 59.94 and 119.88 Hz read as 23, 59 and 119. Kodi treats any n where n+1 is a multiple of 24 or 30 as fractional, (n+1)/1.001, in resolution enumeration, desktop restore and the D3D video sync alike. | check: refresh code applies the same (n+1) % 24 or % 30 rule wherever it reads dmDisplayFrequency, not a fixed list of rates | at: `xbmc/windowing/windows/WinSystemWin32.cpp:CWinSystemWin32::UpdateResolutions`, `xbmc/windowing/windows/VideoSyncD3D.cpp`
- convention: An integer 24, 48 or 60 Hz ChangeDisplaySettingsEx can land on the fractional mode, so for exactly those rates ChangeResolution writes the mode to the registry with CDS_UPDATEREGISTRY|CDS_NORESET, applies it, restores the original registry values, and falls back to a plain CDS_FULLSCREEN change on failure. | check: refresh switching changes keep the registry path for those rates and the registry restore | at: `xbmc/windowing/windows/WinSystemWin32.cpp:CWinSystemWin32::ChangeResolution`
- external: In DISPLAYCONFIG advanced color info, Win11 22H2+ sets advancedColorSupported on SDR screens too, with wideColorEnforced set, and advancedColorEnabled on an SDR screen means Auto Color Management, not HDR. A screen is HDR capable only when advancedColorSupported is set and wideColorEnforced is not. | check: HDR detection checks wideColorEnforced and never reads advancedColorEnabled alone as HDR on | at: `xbmc/platform/win32/DisplayUtilsWin32.cpp:CDisplayUtilsWin32::GetDisplayHDRStatus`
- convention: With videoscreen.usesystemsdrpeakluminance on and a valid Windows SDR white level, GetGuiSdrPeakLuminance returns the cached system value and ignores videoscreen.guisdrpeakluminance. GetGuiSdrPeakLuminance runs every frame. | check: HDR GUI luminance changes handle both settings paths and keep the per-frame read cached | at: `xbmc/windowing/windows/WinSystemWin32.cpp:CWinSystemWin32::GetGuiSdrPeakLuminance`, `xbmc/windowing/win10/WinSystemWin10.cpp:CWinSystemWin10::GetGuiSdrPeakLuminance`
- scenario: The display can change resolution, refresh rate and HDR state at once under Kodi, e.g. when a Remote Desktop session connects. On WM_DISPLAYCHANGE Kodi reapplies display settings if the Windows HDR state no longer matches its output and reapplies RES_DESKTOP when fullscreen; IsTogglingHDR and IsAlteringWindow filter its own changes. | check: display change handling compares against current state and keeps the self-change guard, so Kodi does not loop on its own mode switches | at: `xbmc/windowing/windows/WinEventsWin32.cpp:CWinEventsWin32::WndProc`
- external: On UWP and Xbox, WinRT DisplayInformation must be called from the CoreWindow UI thread; other threads crash. CWinSystemWin10DX records the UI thread id, fills the HDR status cache there, and other threads read the cache. | check: UWP code querying display or HDR state off the UI thread uses the cached values, not WinRT display APIs | at: `xbmc/windowing/win10/WinSystemWin10DX.cpp:CWinSystemWin10DX::IsHDRDisplay`
- convention: The Store build is sandboxed. Library roots (music, video, pictures, documents, removable) use winlib:// on KnownFolders, and a plain local path goes to CWinLibraryFile only when it is in FutureAccessList or MostRecentlyUsedList (granted through a picker); anything else goes to CWin32File and may be denied. | check: file code that works on desktop Windows is checked for UWP, where arbitrary local paths are unreadable without a user grant | at: `xbmc/filesystem/FileFactory.cpp:CFileFactory::CreateLoader`, `xbmc/platform/win10/filesystem/WinLibraryFile.cpp:CWinLibraryFile::IsInAccessList`
