- trap: CSettingsManager::Version is one global value shared by guisettings.xml, every add-on settings file (PVR instance settings too) and the hidden advancedsettings.xml load, which has no version and counts as 0. Any load below Version deep-clones the XML and runs the core migration steps on it, CAddonSettings::Load ignores the updated flag so this repeats on every load, and every save stamps the global version. | check: a new migration step is harmless on add-on settings and advancedsettings.xml, and its old setting id cannot match an add-on setting id | at: `xbmc/settings/lib/SettingsManager.cpp:CSettingsManager::Load`, `xbmc/settings/lib/SettingsMigrationSteps.cpp:BuildMigrationSteps`
- convention: CSettingsManager::Load refuses a file whose version is above its own Version, so a bump locks every guisettings.xml and add-on settings file the new build saves out of older Kodi; downgrades are not supported, so that is accepted. | check: a Version bump is needed, and no add-on specific versioning is invented around it | at: `xbmc/settings/lib/SettingsManager.cpp:CSettingsManager::Load`
- invariant: Renaming or retyping a core setting needs a migration step (dvds.autorun bool to dvds.autoaction int, musicplayer.replaygainpreamp int to replaygainpreampdb number), so an upgrade converts the old value once, logs it and rewrites the file at the new version. | check: a renamed or retyped setting comes with a step rather than dropping the user's value | at: `xbmc/settings/lib/SettingsMigrationSteps.cpp:BuildMigrationSteps`, `xbmc/settings/lib/SettingsMigrationPrimitive.h:ConvertSingleSetting`
- scenario: Stored settings come in a V1 nested form (<settings><a><b>value</b></a></settings> for id a.b) and a V2 flat form (<setting id="a.b">value</setting>), hand-edited to values such as notabool, " true" with a leading space, a lone space, <b></b> or <b />, with extra dots in ids and missing id attributes. | check: migrations and stored-setting readers handle both forms and wrong-type values, and leave the old value in place when conversion fails | at: `xbmc/settings/lib/SettingsMigrationPrimitive.cpp`, `xbmc/settings/lib/test/TestSettingsMigrationPrimitive.cpp`
- invariant [23+]: CSetting::ApplyValue holds the setting's lock only to store or revert the value and runs OnSettingChanging and OnSettingChanged unlocked, so a read during a callback sees the pending value; a revert restores the old value only if the setting still holds this call's value. CSettingList keeps its own copy of the sequence. | check: no setting lock is held across ISettingCallback calls, new setting types write through ApplyValue, and a write made during a rejected change is not lost | at: `xbmc/settings/lib/Setting.cpp:CSetting::ApplyValue`
- trap [22]: CSetting*::SetValue holds the setting's exclusive lock across OnSettingChanging and OnSettingChanged, so a callback that waits on another thread which reads the same setting deadlocks, as setting videoscreen.blankdisplays over JSON-RPC does. | check: a backported setting callback that hops threads (SendMsg to the main thread) while the other side reads that setting | at: `xbmc/settings/lib/Setting.cpp:CSettingBool::SetValue`
